# LunaSight — Scientific Calculation Contract & Implementation Plan

**المرحلة A — تثبيت مواصفات الحسابات العلمية**

**المشروع:** LunaSight\
**التحدي:** CLPS Lunar Mission Browser — NASA Space Apps Challenge 2026\
**التطبيق المستهدف:** Android باستخدام Flutter وDart\
**حالة الوثيقة:** مواصفات أولية قابلة للتنفيذ، مع قائمة تحقق علمية إلزامية قبل
اعتماد النتائج.

---

## 1. الهدف والنطاق

يهدف LunaSight إلى مقارنة مواقع هبوط قمرية وتواريخ مختلفة، من خلال حساب مواضع
الشمس والأرض بالنسبة إلى الأفق المحلي، وتحديد فترات الإضاءة الشمسية ونوافذ الرؤية
الهندسية للأرض.

يجب أن يتيح التطبيق للمستخدم:

1. اختيار موقع هبوط قمري وتاريخ أو فترة زمنية.
2. عرض موضع الشمس والأرض بالنسبة إلى الأفق المحلي.
3. تحديد شروق الشمس وغروبها الهندسيين.
4. تحديد بداية ظهور قرص الأرض واكتمال ظهوره، وبداية اختفائه واكتمال اختفائه.
5. حساب مدد الإضاءة وفترات الرؤية.
6. مقارنة المواقع والتواريخ باستخدام نتائج قابلة للتفسير والتحقق.
7. عرض مصدر البيانات، والافتراضات، ومستوى التحقق من كل نتيجة.

لا يدّعي التطبيق ضمان الاتصال اللاسلكي الفعلي أو إنتاج الطاقة الكهربائية؛ بل يقدم
تقييمًا هندسيًا أوليًا يستند إلى الهندسة الفلكية، مع بيان العوامل التي لم تُنمذج.

## 2. حالة الاختبار المرجعية الحالية

تُستخدم هذه الحالة للتحقق من صحة المحرك الحسابي، ولا تمثل قيدًا على المواقع التي
سيدعمها التطبيق.

| المعامل                                | القيمة                |
| -------------------------------------- | --------------------- |
| الجسم المركزي                          | Moon                  |
| الجسم المستهدف                         | Earth                 |
| إطار الإحداثيات                        | MOON_ME               |
| نوع الموقع                             | Fixed point           |
| خط الطول Planetodetic                  | −160°                 |
| خط العرض Planetodetic                  | −88.45°               |
| الارتفاع                               | 0 km                  |
| الإطار المحلي                          | Topocentric at point  |
| تصحيح زمن الضوء                        | To observer           |
| خوارزمية زمن الضوء                     | Converged Newtonian   |
| تصحيح الانحراف النجمي                  | Corrected             |
| الزمن المعروض                          | UTC                   |
| إصدار State Vector المستخدم في التجربة | solar_system_v0071.tm |
| إصدار Angular Size المستخدم في التجربة | solar_system_v0070.tm |

**قيد مهم:** يجب توحيد مصدر بيانات الحسابين قبل اعتماد التوقيت النهائي. كما يجب
التحقق من أن إطار `MOON_ME` المستخدم في الأداة هو الإطار المقصود نفسه في جميع
عمليات الحساب.

## 3. تعريف الإحداثيات والزمن

### 3.1 الإحداثيات

- تخزين إحداثيات الموقع في نموذج واضح يتضمن خط الطول وخط العرض والارتفاع ونوع
  الإحداثيات.
- عدم افتراض أن Planetodetic وPlanetocentric متطابقان.
- توثيق اتجاه المحاور وتعريف الإطار المرجعي.
- حساب ارتفاع الجسم نسبةً إلى المستوى المحلي العمودي على اتجاه الشاقول عند نقطة
  الهبوط.
- اعتبار الأفق في الإصدار الأول أفقًا هندسيًا مثاليًا، لا أفقًا تضاريسيًا مستخرجًا من
  خرائط الارتفاعات.

### 3.2 الزمن

يجب فصل المقاييس الزمنية التالية داخل النظام:

- UTC: لعرض التواريخ والأوقات للمستخدم.
- TT/TDT: إذا كانت واجهة المصدر تستخدمه في إدخال أوقات الحساب.
- TDB: عند الحاجة إلى الزمن الديناميكي المستخدم في عمليات SPICE.

يجب أن تكون جميع التحويلات صريحة وقابلة للاختبار. لا يجوز التعامل مع UTC وTT وTDB
باعتبارها أوقاتًا متطابقة.

يجب تخزين كل حدث مع مقياسه الزمني، ومصدره، ودقته المعلنة.

## 4. مواصفات حساب موضع الشمس والأرض

لكل جسم ولكل وقت مطلوب، يجب توفير:

| المخرج                  | الوحدة | الوصف                                                        |
| ----------------------- | ------ | ------------------------------------------------------------ |
| Azimuth                 | درجة   | اتجاه الجسم بالنسبة إلى تعريف الشمال المحلي                  |
| Elevation               | درجة   | ارتفاع مركز الجسم بالنسبة إلى المستوى الأفقي المحلي          |
| Range                   | كم     | المسافة إلى الجسم المستهدف                                   |
| Angular radius          | درجة   | نصف القطر الزاوي الظاهري، وفق تعريف هندسي موثق               |
| Angular diameter        | درجة   | القطر الزاوي، ويساوي ضعفي نصف القطر عند استخدام تعريف متناظر |
| Apparent/geometric mode | —      | بيان نوع الإحداثيات والتصحيحات المستخدمة                     |
| Timestamp               | UTC    | وقت العينة أو الحدث                                          |

لا يجوز الخلط بين ارتفاع مركز الجسم وارتفاع حافته، أو بين القطر الزاوي ونصف القطر
الزاوي.

يجب أن يكون تعريف كل مخرج ثابتًا داخل المحرك، حتى لو اختلفت تسميات الأعمدة في
الأدوات المرجعية.

## 5. مواصفات أحداث الأفق

يرمز \(h\) إلى ارتفاع مركز الجسم، ويرمز \(r\) إلى نصف قطره الزاوي.

### 5.1 الأرض

بالنسبة إلى قرص الأرض، وفق نموذج قرص زاوي تقريبي:

| الحدث                       | شرط التماس                         |
| --------------------------- | ---------------------------------- |
| بداية الظهور أثناء الشروق   | \(h+r=0\)، مع عبور باتجاه الظهور   |
| اكتمال الظهور               | \(h-r=0\)، مع عبور باتجاه الظهور   |
| بداية الاختفاء أثناء الغروب | \(h-r=0\)، مع عبور باتجاه الاختفاء |
| اكتمال الاختفاء             | \(h+r=0\)، مع عبور باتجاه الاختفاء |

يجب تحديد اتجاه العبور، لأن مجرد تحقق المعادلة لا يكفي لتصنيف الحدث.

هذه المعادلات تمثل نموذجًا زاويًا مبسطًا. يجب مراعاة شكل الأرض الإهليلجي عند الحاجة
إلى دقة أعلى، وعدم استخدام نصف قطر استوائي ثابت باعتباره نموذجًا كاملًا للشكل
الظاهري للأرض.

### 5.2 الشمس

يجب فصل حدثين مختلفين:

1. **الشروق والغروب الهندسيان لمركز الشمس:** عبور ارتفاع المركز للصفر.
2. **بداية الإضاءة ونهايتها بالنسبة إلى قرص الشمس:** استخدام نموذج الحافة الشمسية
   المناسب بدلًا من الاكتفاء بعبور المركز.

في النموذج الزاوي المبسط، يبدأ ظهور الحافة العليا للشمس عندما \(h+r=0\)، وتكتمل
رؤية القرص عندما \(h-r=0\)، مع مراعاة اتجاه العبور.

يجب عدم وصف أوقات الشروق والغروب بأنها أوقات إضاءة فعلية كاملة إذا كانت التضاريس
المحلية أو الظلال غير ممثلة في النموذج.

## 6. تحديد زمن الحدث

لا يكفي استخدام أقرب صف في جدول زمني بفاصل دقيقة واحدة لتحديد وقت تماس دقيق.

يجب أن ينفذ المحرك الخطوات التالية:

1. مسح الفترة الزمنية بعينات مناسبة لاكتشاف تغيّر حالة الحدث.
2. تحديد الفترة المحصورة التي تحتوي على عبور محتمل.
3. تقييم دالة الحدث على جانبي العبور.
4. استخدام طريقة عددية لإيجاد الجذر، مثل Bisection أو Brent، أو استخدام أداة بحث
   أحداث موثقة من SPICE.
5. التحقق من اتجاه العبور.
6. إعادة تقييم الحالة عند الوقت المحسوب.
7. حفظ خطأ التقارب أو حد عدم اليقين إن كان متاحًا.

يجب اختيار خطوة المسح بناءً على أقصر مدة حدث مطلوب اكتشافه، لا بافتراض أن خطوة
دقيقة واحدة مناسبة لكل الحالات.

يجب أن تكون طريقة البحث قادرة على التعامل مع غياب الحدث، وتعدد الأحداث، والتماس
دون عبور واضح، والفترات التي لا تتوافر لها بيانات كافية.

## 7. مصدر البيانات وتوحيد الحسابات

يُستخدم JPL Horizons مرجعًا للحصول على بيانات فلكية قابلة للمقارنة، مع توثيق
إعدادات الاستعلام وملفات kernels المستخدمة.

قبل اعتماد أي نتيجة، يجب توثيق:

- الجسم المستهدف والمراقب.
- موقع المراقب وإطار الإحداثيات.
- نوع الإحداثيات: هندسية أو ظاهرية.
- تصحيح زمن الضوء والانحراف النجمي.
- نموذج شكل الجسم.
- إصدار ephemeris أو kernel المتاح.
- مقياس الزمن.
- الفترة الزمنية وخطوة أخذ العينات.
- الوحدات وتعريف كل عمود.

لا يجوز دمج بيانات مأخوذة من إصدارات kernels مختلفة ثم وصف النتيجة بأنها متحققة
نهائيًا، ما لم يُجرَ اختبار يوضح أثر الاختلاف.

إذا تعذر توحيد الإصدارات، يجب تسجيل ذلك كقيد، وإجراء مقارنة مستقلة ضمن حدود
البيانات المتاحة.

## 8. تصحيح الحالة التجريبية الحالية

التقدير السابق لبداية اختفاء قرص الأرض، قرابة `2026-11-01 07:40:30 UTC`، **ليس
نتيجة معتمدة**.

الأسباب:

1. لم يُحسم بصورة موثقة تفسير القيمة الناتجة عن خيار `Maximum radius`.
2. بيانات الارتفاع والمسافة مأخوذة من State Vector، بينما الحجم الزاوي مأخوذ من
   أداة أخرى وإصدار kernel مختلف.
3. الحساب باستخدام نصف القطر الاستوائي للأرض يفترض نموذجًا كرويًا مبسطًا.
4. التقارب بين توقيتين تقديريين لا يثبت صحة أي منهما، خصوصًا إذا كانا يشتركان في
   بيانات ارتفاع المركز نفسها.

يجب إعادة حساب هذا الحدث باستخدام تعريف موثق لنصف القطر الزاوي، ونموذج جسم متسق،
وإعدادات مرجعية يمكن إعادة إنتاجها.

لا يُعرض التوقيت السابق باعتباره نتيجة علمية نهائية داخل التطبيق.

## 9. حساب الإضاءة الشمسية

يجب أن ينتج المحرك، لكل موقع وفترة زمنية:

- أوقات بداية الإضاءة ونهايتها وفق تعريف الحافة المختار.
- مدد الإضاءة المتصلة.
- مدد الظلام.
- عدد فترات الإضاءة خلال الفترة المطلوبة.
- ارتفاع الشمس عند أوقات يحددها المستخدم.
- الحد الأدنى والأقصى لارتفاع الشمس خلال الفترة، عند حسابهما.

يمكن استخدام هذه النتائج لتقدير فرص تعرض الألواح الشمسية للضوء، لكن حساب الطاقة
الكهربائية الفعلية يحتاج إلى معطيات إضافية مثل اتجاه اللوح ومساحته وكفاءته
وخصائص الظلال والبيئة الحرارية.

## 10. حساب نوافذ الرؤية الهندسية للأرض

لكل موقع وفترة زمنية، يجب حساب:

- أوقات بداية ظهور الأرض واكتمال ظهورها.
- أوقات بداية اختفائها واكتمال اختفائها.
- مدة الرؤية الهندسية.
- عدد نوافذ الرؤية.
- ارتفاع مركز الأرض أثناء النوافذ.
- المسافة إلى الأرض عند الأوقات المطلوبة.

يجب التمييز بين الرؤية الهندسية وإمكانية الاتصال الفعلي. لا يجوز اعتبار الأرض مرئية
هندسيًا دليلًا كافيًا على توافر رابط اتصالات؛ فذلك يحتاج إلى بيانات عن التضاريس
والهوائيات والقدرة والترددات ومتطلبات الرابط.

## 11. المقارنة بين المواقع والتواريخ

يجب أن يعتمد ترتيب المواقع على معايير معلنة، مثل:

- إجمالي مدة الإضاءة خلال الفترة المختارة.
- أطول مدة إضاءة متصلة.
- إجمالي مدة الرؤية الهندسية للأرض.
- أطول نافذة رؤية متصلة.
- عدد فترات الانقطاع.
- مستوى اكتمال البيانات ودرجة التحقق.

لا يجوز إنشاء درجة إجمالية للموقع قبل توثيق طريقة الوزن والتطبيع لكل معيار.

يجب إظهار القيم الأصلية بجانب أي درجة مركبة، حتى يتمكن المستخدم من فهم سبب تفضيل
موقع على آخر.

## 12. حالات الاختبار العلمية

يجب إنشاء مجموعة اختبارات مستقلة تشمل:

1. جسم مرتفع بوضوح فوق الأفق.
2. جسم منخفض بوضوح تحت الأفق.
3. عبور ارتفاع المركز للصفر.
4. عبور الحافة العليا أو السفلى للأفق.
5. جسم لا يحدث له عبور خلال الفترة المختارة.
6. أكثر من حدث داخل الفترة نفسها.
7. تماس تقريبي دون عبور واضح.
8. فترة لا تتوافر لها بيانات فلكية كافية.
9. اختلاف إصدار البيانات المرجعية.
10. حالات خاصة قرب القطبين أو عند ارتفاعات شديدة الانخفاض.

يجب مقارنة النتائج بحالات مرجعية محفوظة، وليس بقيم تقريبية مكتوبة يدويًا داخل
الاختبارات.

## 13. شروط قبول المحرك الحسابي

لا يُعتبر المحرك جاهزًا للدمج النهائي إلا إذا:

- اجتاز اختبارات المعادلات والوحدات والتحويلات الزمنية.
- أعاد إنتاج الحالات المرجعية ضمن حدود تفاوت معلنة.
- تحقق من اتجاه العبور وتصنيف الحدث.
- تعامل مع البيانات المفقودة والأخطاء دون إنتاج نتائج مضللة.
- حفظ بيانات المصدر والإعدادات اللازمة لإعادة الحساب.
- ميّز النتائج المحسوبة والنتائج المرجعية والتقديرات غير المتحقق منها.
- لم يستخدم ثواني أو أجزاء درجات إضافية بما يوحي بدقة أعلى من الدقة الفعلية.

لا تُحدد حدود تفاوت نهائية لكل الحسابات قبل معرفة دقة المصدر ونموذج الجسم ونوع
الحدث؛ بل يجب تحديدها وتوثيقها لكل اختبار.

## 14. المتطلبات المعمارية للتنفيذ

يجب أن يفصل مشروع Flutter بين:

- **Domain:** نماذج المواقع والأجسام والأحداث، وتعريفات الحسابات وقواعد التصنيف.
- **Data:** مصادر البيانات الفلكية، وتحويل الوحدات والأزمنة، وتخزين النتائج
  المرجعية.
- **Calculation Engine:** حساب الارتفاعات والحجوم الزاوية والأحداث والفترات.
- **Validation:** الاختبارات المرجعية، وفحوص الاتساق، وتصنيف حالة التحقق.
- **Presentation:** الواجهات والجداول والمقارنات والرسوم الزمنية.

لا يجوز ربط واجهات المستخدم مباشرة بتفاصيل مصدر البيانات أو بمنطق حساب الحدث.

يجب أن يكون مصدر البيانات قابلًا للاستبدال دون إعادة كتابة قواعد الحساب، وأن يكون
المحرك قابلًا للاختبار دون تشغيل واجهات Flutter.

## 15. عرض النتائج للمستخدم

يجب أن تتضمن كل نتيجة علمية:

- اسم الموقع وإحداثياته.
- الجسم المستهدف.
- وقت الحدث بوحدة UTC.
- تعريف الحدث.
- مصدر البيانات وإعدادات الحساب.
- مستوى التحقق.
- الافتراضات والقيود ذات الصلة.

يجب الفصل بصريًا بين النتائج المعتمدة، والنتائج التقديرية، والنتائج التي لا تزال
قيد التحقق.

شروط التحقق المناسبة لكل حساب.
